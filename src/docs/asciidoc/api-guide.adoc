Vointika's HTTP API. Requests and responses are JSON. Every example below is
generated from the controller documentation tests, so the guide never drifts
from the running service.

[[overview]]
== Overview

[[overview-http-status-codes]]
=== HTTP Status Codes

|===
| Status code | Usage

| `200 OK`
| The request completed successfully.

| `201 Created`
| A new resource was created; its location is in the `Location` header.

| `204 No Content`
| The request completed successfully with no response body.

| `400 Bad Request`
| The request could not be read: a malformed body, or a path/query value of the wrong type (a `{id}` that is not a UUID). Distinct from `422`, which means the body parsed but a field is invalid.

| `401 Unauthorized`
| Missing or invalid authentication credentials.

| `403 Forbidden`
| Authenticated, but not permitted (e.g. an insufficient tour-operator role).

| `404 Not Found`
| The resource was not found — or is hidden for tenant isolation (a non-member sees the same 404 as a missing operator).

| `409 Conflict`
| The request conflicts with current state (e.g. a duplicate, or an already-accepted invitation).

| `410 Gone`
| The resource is no longer available (e.g. a revoked or expired invitation).

| `422 Unprocessable Content`
| The request body contains invalid fields.

| `429 Too Many Requests`
| A rate limit was exceeded (see <<overview-rate-limiting>>).

| `500 Internal Server Error`
| An unexpected error occurred.
|===

[[overview-errors]]
=== Error Responses

Every error response has the same shape:

|===
| Field | Type | Description

| `status`
| Number
| The HTTP status code.

| `error`
| String
| The HTTP status reason phrase.

| `message`
| String
| A human-readable error message.

| `code`
| String
| Optional stable, machine-readable error code. Present only when the throw site supplies one (certain `422`/`409` errors); omitted otherwise. Clients that branch on a specific cause should match this rather than the human-readable `message`.

| `timestamp`
| String
| When the error occurred (ISO 8601).
|===

[[overview-resource-identity]]
=== Resource Identity

Every resource-representing response identifies itself with two meta fields:

* `id` — the entity's id. Always literally `id`, never a prefixed name.
* `context` — the collection the entity belongs to (`"users"`, `"currencies"`,
  `"timezones"`, …). A team member is a user with a role, so a member row is
  `id` (the user's id) + `context: "users"`.

[[overview-lists]]
=== Lists

Every endpoint marked "cursor-paginated" takes the same three query parameters
and **nothing else**:

[cols="1,3"]
|===
| `filter[field][op]` | A filter. The fields and the operators each one allows
are listed per endpoint — e.g. `filter[status][in]=DRAFT,PUBLISHED`.
| `sort` | A sortable field, `-` prefixed for descending: `sort=-createdAt`.
Each endpoint lists what it sorts by, and its default.
| `cursor` | The opaque `nextCursor` from the previous page. `nextCursor` is
`null` on the last page.
|===

The page size is fixed and identical for every list; there is no parameter to
change it.

Anything else is `422` — including a misspelled parameter name. So is an unknown
filter field, an operator a field does not allow, a sort field that is not
sortable, and a negating operator (`neq`, `not_contains`, `not_in`) on a field
that may have no value. A list never silently ignores part of a request.

That last one is a refusal rather than a limitation of the parser. A row with no
value cannot be matched by a negative filter — in SQL it is neither equal nor
unequal to anything — so answering would mean returning a list that is quietly
short. Endpoints below name the fields this applies to; the positive operators
work on them as normal.

[[overview-authentication]]
=== Authentication

Authenticated endpoints require a `Bearer` access token:

----
Authorization: Bearer <access-token>
----

Obtain one from <<resources-login>>. A short-lived access token is refreshed via
<<resources-refresh>> using the `httpOnly` refresh cookie. Endpoints under
`/api/tour-operators/{id}/**` additionally require membership of that operator
(a non-member is indistinguishable from a missing operator — both `404`); the
role each action needs (member / ADMIN+ / OWNER) is noted per endpoint.

[[overview-unauthorized]]
==== Without a Token

Every authenticated endpoint answers the same way, because the refusal happens in
the security filter chain before any controller runs. It is the ordinary error body,
and **no 401 in this API carries a `code`** — whichever layer produced it. The
message never says which part of the credential failed.

[[overview-rate-limiting]]
=== Rate Limiting

The public authentication endpoints are rate-limited per IP, with additional
per-account throttles inside the identity flows. Exceeding a limit returns
`429 Too Many Requests`.

[[resources-refresh-invalid]]
==== Refresh Access Token — Rejected

**Three causes, and one of them ends every session you hold.** An expired token
says so — `Refresh token has expired`. An unknown token and a **replayed** one
are deliberately indistinguishable, both answering `Invalid refresh token`,
because telling a caller they tripped the reuse detector would tell an attacker
the same thing.

The consequence differs sharply. A replayed token — one already rotated away — is
treated as a theft signal, and **the entire token family is revoked**: every
session descended from that login ends, not just this one. Retrying a refresh
with a token you already exchanged lands here.

**A genuine simultaneous double-submit does not.** If two tabs present the *same
live* token at once, the loser gets a plain 401 and the family survives — the
rotation is guarded precisely so racing clients are not logged out of everything.
You do not need a mutex around refresh; you do need to treat a 401 as "start
again at login" rather than "retry with the same token".

[[resources-touroperator]]
=== Tour Operators

[[resources-create-operator]]
==== Create Tour Operator

The authenticated caller becomes the operator's OWNER.

operation::tour-operators/create[]

**Creating a store does more than store a name**, and none of it is in the
response — the 201 carries only a `Location`. Read the operator back to see any
of it:

* A **handle** is generated from the name. It is the storefront subdomain and it
  is not editable afterwards. A collision is suffixed silently, so a second
  "Sunset Tours" becomes `sunset-tours-2` rather than being refused.
* The store is **password-protected from the moment it exists**, with a
  generated password, the way a new Shopify store is. It answers the gate page,
  not the shop, until an ADMIN turns protection off — see
  <<resources-operator-password-update>>.
* Two menus already exist: `main-menu` and `footer`. They are ordinary menus and
  can be renamed or deleted, but creating one with either handle is a 409.

[[resources-create-operator-conflict]]
==== Create Tour Operator — Name Already Used

409. One name per owner: creating a second operator with a name you already use
is refused, which is what makes a double-submitted form safe. Two *different*
owners may both run "Sunset Tours" — the check is scoped to you.

Public — validates the emailed token before the accept form.

operation::invitations/preview[]

[[resources-invitation-preview-gone]]
==== Preview an Invitation — Link No Longer Valid

**410 Gone, the only one in this API.** An accept link lasts seven days, and a
resend mints a fresh token that kills the previous one — so an older email in the
same thread is a dead link rather than a wrong one. Revoking has the same effect.

410 rather than 404 on purpose: it says "this existed and is over", so the client
tells the invitee to ask for a new invitation instead of offering a retry. An
unknown token — one that never existed — is a 404.

==== Accept an Invitation — You Already Have an Account

409, and **the most common way this flow fails**. Someone with a Vointika account
who opened the link while logged out and filled in the name-and-password form
lands here: the endpoint will not set a password on an account that has one.

an authenticated accept needs no body at all.

[[resources-members-change-role]]
==== Change a Member's Role

ADMIN+ for ADMIN and STAFF.

**OWNER is not a role you grant — it is a transfer, and it costs you the store.**
Sending `{"role":"OWNER"}` promotes that member and **demotes you to ADMIN in the
same transaction**. Only an owner may send it, and only the new owner can hand it
back. An admin UI should not put OWNER in the same dropdown as the other two
without saying this.

An ADMIN may change any ordinary member's role and is refused on the owner's.
Nobody changes their own role, whatever it is.

operation::tour-operators/members/change-role[]

[[resources-members-change-role-forbidden]]
==== Change a Member's Role — Only an Owner Touches the Owner

403. The membership check has already passed here, so this is a line *inside* a
permission an admin has: they may edit every member except the owner.

operation::tour-operators/members/change-role-forbidden[]

[[resources-members-change-role-conflict]]
==== Change a Member's Role — Not Your Own

409. The endpoint refuses your own id whatever role you send. An owner who tries
gets a different message — transfer ownership first — because stepping down and
leaving the store ownerless are the same act. The transfer demotes you as part of
the same call, so that is the way down.

operation::tour-operators/members/change-role-conflict[]

STAFF member can leave — so the role gate applies only when the id is someone
else's. Only an owner may remove an owner.

[[resources-members-remove-conflict]]
==== Remove a Member — The Last Owner Stays

409, from either side: the sole owner cannot leave, and an admin cannot remove
them. A store always has exactly one owner. Transfer ownership first — see
<<resources-members-change-role>>.

[[resources-operator-get]]
==== Get the Operator

Any member. The operator's own details.

operation::tour-operators/get[]

[[resources-operator-update]]
==== Update the Operator

ADMIN+ only. An absent field is unchanged; a blank string clears an optional one
(phone, email). `handle` is not editable — it is the storefront subdomain.

**Changing `timezoneId` re-times the operator's whole published schedule.**
Departures store operator-local wall-clock with no zone, so a 10:00 sailing stays
"10:00" and now means a different instant — and nothing rewrites the stored rows.
`CreateSlotUseCase`'s past-date guard also begins judging against a different
today.

That is deliberate, and it is exactly right for an operator correcting a mis-set
timezone. It is exactly wrong for one that genuinely moved, and the API does not
distinguish the two. The audit entry carries the before and after, so the change
is at least traceable.

[[resources-policies-create-forbidden]]
==== Create a Store Policy — STAFF May Not Write

403, and **the shape of the role boundary across this whole section**. A STAFF

this section's endpoints gate on ADMIN+ or OWNER and answer exactly this way.

caller *is* a member, just not a senior enough one. A non-member gets
<<resources-invite-not-found>> instead, and never learns the operator exists.

[[resources-menus-replace-items]]
==== Replace a Menu's Items

ADMIN+ only. Writes the whole tree at once: every item is validated before any is
written, ids are fresh on each save, and one audit event is recorded. EXPERIENCE
and PAGE targets must belong to this operator → 422.

The nesting cap is stated in the `items` description below and in the refusal
under <<resources-menus-replace-items-invalid>>, both generated from
`MenuItem.MAX_DEPTH`. It is deliberately not written out here as well: it was, in
four published places, and raising the cap would have moved the enforcement and
left every one of them saying the old number.

operation::menus/replace-items[]

[[resources-menus-replace-items-invalid]]
==== Replace a Menu's Items — Invalid Tree

422. Nesting past the cap, a link type that does not match the fields sent, a
resource id from another operator, or a translation for a locale the operator

**Two different handles collide here, and only one of them is visible to the

[[resources-metafield-translations]]
=== Metafield Translations

Per-locale overlays for metafield *values*. A value with no translation in the
locale being served falls back to the canonical one, per key — so an operator who
has translated two of five metafields gets two translated and three canonical.

Three things are fixed by design:

* **Only text types can be translated** — `single_line_text` and
  `multi_line_text`. A translated `true` is `true` and a translated `2026-08-13`
  is the same date, so every other type is a 422 naming the key. A
  `metaobject_reference` is not a gap either: pointing at a different entry per
  locale is content *selection*, not translation — translate the entry's own
  fields instead.
* **The whole locale is written at once**, keyed `namespace.key`. A blank value
  clears that key; a key left out of the payload is untouched, so a partial form
  cannot delete what it never rendered.
* **Nothing is written when anything is invalid.** Half a translated locale is
  worse than a rejected save, because nothing tells the operator which half
  landed.

The path is `metafield-translations`, not `metafields/translations`: the latter
collides with `/metafields/{namespace}/{key}`.

The role check runs first, so this is what an ADMIN sees when the message is

[[resources-contact-delete-forbidden]]
==== Delete a Contact Message — Forbidden

**Reading the inbox and deleting from it have different bars.** Any member can
list and read a message; only ADMIN+ can delete one. So a STAFF caller can see a
message and be refused when deleting it, and this is the answer they get.

=== Audit Log

Every operator-facing mutation, append-only.

[[resources-audit-list]]
==== List Audit Entries

Any member; non-member → 404. Cursor-paginated, tenant-scoped. Filter by `action`, `actorId`,
`actorName`, `actorType`, `entityId`, `entityType` and/or `createdAt`; sort by
`id` (default, newest first) or `createdAt`; page with `cursor`.

`actorId` and `actorName` may have no value — a `SYSTEM` entry has no user
behind it, and a deleted account no longer resolves to a name. The negating
operators are therefore unavailable on those two fields and answer `422`:
`not_in` on `actorId`, `neq` and `not_contains` on `actorName`.

operation::audit-log/list[]

[[resources-audit-get]]
==== Get an Audit Entry

Any member. Non-member → 404.

operation::audit-log/get[]

[[resources-audit-get-not-found]]
==== Get an Audit Entry — Not Found

An entry id that does not exist, and one belonging to another operator, answer
identically. That is deliberate: a 404 that varied would tell a caller which ids
exist elsewhere. This is the application's error shape, the same on every endpoint.
